Systems I designed & led
Fulfilment Capacity Redesign

Capacity used to be checked only against courier capacity per day. I redesigned it to also check warehouse-level daily capacity and whether the warehouse is working that day, covering public holidays, recurring non-working days, and ad hoc closures. The result is a delivery promise at checkout that is close to 100% accurate. I wrote the technical design: a dual capacity model, forecasting, an audit trail, and datetime-level granularity for delivery time slots.

ATLAS — Fulfilment Capacity page

Proposed, designed, and added the Fulfilment Capacity page to ATLAS, the internal warehouse app (Next.js front end, with Next.js and Spring Boot APIs). Warehouses use it to add, edit, and remove capacity for a date range or a specific date, and to manage public holidays, recurring, and ad hoc non-working days. It is the source of truth for the new capacity check.

Next.js UI→Next.js API (new)+Spring Boot API (existing)→capacity check at checkout
courier-event-comms

Event-driven Cloud Run function in NestJS that subscribes to courier events. For same-day on-board events with an orderId and customerId, it fetches the order details from the order API, transforms them, and publishes to a topic that Braze listens to. Braze then notifies the customer by SMS and email.

Pub/Sub→NestJS fn→Order API→Pub/Sub→Braze
delivery-code-update

Cloud Run function in NestJS that keeps delivery codes in sync between Minpin and Commercetools. Minpin is the legacy JSP/JSF warehouse app being gradually migrated to ATLAS. It publishes a message whenever a delivery code changes, and the function updates Commercetools when needed. Delivery codes drive both the delivery promise and special discounts, so both stay accurate.

Minpin→Pub/Sub→NestJS fn→Commercetools
Delivery Feedback MCP

MCP server called by the Gladly AI customer-service agent. It captures non-serious delivery feedback for orders dispatched and delivered within the last 30 days and posts it to Nash, the courier platform, to review delivery and driver performance. It also publishes each record to a Pub/Sub topic with a BigQuery subscription, so CX moved from tracking feedback in spreadsheets to querying it in BigQuery for metrics and analytics.

My rules for working with AI

✅ Verify everything

When AI isn't sure, it guesses. Integrating an internal system with Commercetools, it invented field and object names that don't exist. I check every output against the real schema and docs.

- customer.custom.fields.deliveryZoneCode // AI guess: field not in type
+ customer.custom.fields.deliveryCode // verified against schema
🔒 No secrets, ever

Credentials, API keys, and other secrets never go into a prompt or an AI tool's context.

🧑‍💻 I own the implementation

AI assists; I'm accountable. Every change is driven by the business rules and requirements, not by what the model suggests.
